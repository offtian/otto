# Implementation Plan: Otto — Slack-native Tech-Support Agent

## Project goal

Otto is an API-first tech-support agent: a FastAPI service driving an OpenAI Agents SDK agent that answers knowledge-base questions with citations over a **verified read-only** Confluence toolset, walks users through markdown runbooks with multi-turn context rebuilt from the conversation, submits SailPoint access requests **only** after a role-authorized human approves via a Block Kit card, and escalates everything else with structured context. It meets employees on **two channels from MVP**: Slack mentions/DMs and tickets filed in Jira (D8/D9) — ticket comments are its reply channel, ticket transitions are policy-gated (D10). **Otto is currently a personal prototype for idea formulation (D7)** — firm-perimeter items are tagged `[GRADUATION]` and block nothing until Otto becomes a firm deliverable; phases are a sequence, not a calendar.

| Risk | Fallback (concrete) |

| In-memory approvals lost on restart | Accepted for the prototype — the card persists in Slack and the requester re-asks; eliminated by 2.2 |
| Gateway rate limits / model quality | Load-test via the LiteLLM stand-in; the eval set is the regression net — a model swap is one `.env` value |
| Slack retry storms / duplicate events | event-id/ts dedup (0.4) for single-replica; Redis dedup (3.5) before multi-replica |

## Overall acceptance criteria

Directional while Otto is a prototype; they become hard gates at graduation (PRD §8).

1. `just lint && just test && just eval` green, with the D5-chosen gate enforcing ≥ 90% pass at n ≥ 20 golden cases (NFR3).
2. Resolution rate (per D6 + the T2 signal) ≥ 30% across both channels where Otto runs, reported from traces + escalation counts + resolution signals (including ticket status).
3. Intake ack fast on every channel (Slack < 3s) and time-to-first-response < 15s, read from OTel spans (NFR1).
4. **Zero unapproved sensitive writes — ever** — demonstrated by the Phase 2 audit report over the first 50 access requests, with every mounted sensitive tool verified to pause; ticket transitions gated per D10 until the sensitivity policy classifies them.
5. Every agent run, tool call, and LLM generation traced to Logfire and/or OTLP (D4); PII scrubbing in place before any real-data pilot (graduation gate).
6. FR8 holds end-to-end on both channels: a forced failure anywhere in the pipeline still yields a user-visible reply at the origin and an alert — no silent drops; no bot reply loops.
7. New integrations require only a `vendors/` adapter + `config.py` wiring — proven in practice by the Phase 3 ServiceNow adapter landing with zero agent changes (NFR5).
