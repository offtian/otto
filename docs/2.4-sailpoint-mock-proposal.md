# 2.4 — SailPoint mock MCP: proposed tool surface (T8) — for review

**Status:** proposal, awaiting your sign-off. Nothing built yet. 2.4 is the last
gate before the access-automation loop runs end-to-end against something that
behaves like SailPoint. There is no public SailPoint dev image, so we build a
small mock MCP service (compose note already flags this at `compose.yml:63`).

## What 2.4 has to prove

- A `require_approval="always"` MCP server so **every mounted tool pauses** for
  HITL before it executes (already wired in `vendors/mcp.py::build_sailpoint`).
- A **gate-coverage test**: verify 100% of the mock's mounted tools actually
  interrupt the run — tested against the *real* mounted tool list, not
  assumptions (this is the project's worst-failure guard: a write slipping past
  the gate).
- Eval cases for the collect-justification dialogue (the agent gathering
  system + entitlement + justification before it submits).

## Proposed tool surface (the T8 decision)

Recommended **minimal** surface — just what Otto's flow actually needs:

| Tool | Params | Returns | Kind | Gated? |
|---|---|---|---|---|
| `request_access` | `system`, `entitlement`, `justification` | request id + "submitted" | **write** | **yes** (always) |
| `get_access_request_status` | `request_id` | `pending` / `approved` / `provisioned` / `denied` | read | yes (2.4), un-gate at 2.6 |

- **`request_access`** is the one that matters — it's the FR4 write, and it maps
  1:1 to today's in-process stub (`domain/support/agent.py::request_access`), so
  the agent instructions need **no change** if the mock names it `request_access`.
  When `SAILPOINT_MCP_URL` is set, this MCP tool replaces the stub automatically
  (`build_agent` drops the stub when the server is mounted).
- **`get_access_request_status`** is optional but cheap; it lets a follow-up
  ("did my access come through?") be answered. It's a read, so under 2.4's
  blanket `require_approval="always"` it would *also* pause — mildly awkward but
  safe. It becomes un-gated when 2.6 introduces the per-tool policy.

**Deferred / probably unnecessary** (flagging so you can pull them in if you
disagree): `search_entitlements(system, query)` and `list_identity_access(identity)`.
The agent already discovers the right entitlement name by searching the
**Confluence** KB (per its instructions), so a SailPoint search tool likely
duplicates that. Leaving them out keeps the gated surface small and the
gate-coverage test tight.

## How the mock would be built & wired

- A ~40-line **FastMCP** Python service (streamable-HTTP, like `mcp-confluence`),
  added under a `sailpoint` compose profile; `SAILPOINT_MCP_URL` points at it.
  It holds submitted requests in memory and returns deterministic ids/status so
  eval + gate tests are stable.
- No code change in `vendors/mcp.py` (the `require_approval="always"` server is
  already there) — 2.4 is: the mock service + wiring + the gate-coverage test +
  eval cases.

## Questions for you (T8 sign-off)

1. **Surface:** the minimal two tools above, or do you want the read/search
   tools (`search_entitlements`, `list_identity_access`) in the mock too?
2. **Gating of reads:** keep 2.4's blanket "everything pauses" (simplest, safest,
   reads pause too) — or should `get_access_request_status` be un-gated from the
   start (which pulls a slice of 2.6's per-tool policy forward)?
3. **Tool name:** confirm the write tool is named `request_access` (zero agent
   changes) rather than a SailPoint-native name like `submit_access_request`
   (which would need an instruction + eval-case update).
4. **Sign-off owner:** who signs off future changes to the sensitive-tool list
   (this feeds 2.6's "policy changes may only widen the gated set" rule)?
